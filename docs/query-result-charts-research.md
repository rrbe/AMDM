# MongoDB 查询结果图表调研

调研日期：2026-11-13。产品能力以官方文档为依据，未安装竞品逐项实测。

## 当前实现

首版已提供查询结果的柱状图、折线图、饼图，按当前页选择顶层字段绘制，字段配置统一使用「维度 / 指标」（Dimension / Metric）。每个结果独立保留配置，图表与表格切换不会重新执行脚本。柱状图和折线图在坐标轴标明维度、指标及所选字段，饼图在画布内显示指标标题与维度说明。嵌套字段先通过 `$project` 提取到顶层，数组先通过查询展开。

图表库按需加载；字段下拉最多挂载 100 个匹配项，搜索覆盖所有已发现字段。饼图图例仅用于识别维度值，占比分母保持整个绘图范围。缺失值、无效数值、Decimal 近似值及饼图维度值重复有明确提示。

本地已通过类型检查、89 项相关单元测试、生产构建及 macOS arm64 Electron 原生验证。原生用例覆盖真实 MongoDB 聚合、三种图形、配置保留、无重复执行、分页范围、暗色与缩放、Decimal、500 字段检索及 2000 点折线图。原生报告位于 `dist/e2e-validation/query-charts/`。

## 结论

已有数据库客户端把查询结果直接转换成图表。AMDM 可以将其定位为结果区的 Chart 视图：执行查询后选择字段，用柱状图、折线图或饼图观察结果。

需要先区分两种需求：已经汇总好的数据直接画图，以及从原始明细中生成统计结果。前者适合先做；后者涉及分组、聚合和查询范围，需要独立定义语义。

## 第一版设计

### 入口和操作

在现有 Tree / JSON / Table 旁增加 Chart，模式名称统一使用英文。在结果区域内展示图表，配置面板保持固定布局。

基本操作：执行查询 → 切换 Chart → 选择图表类型 → 选择维度字段和指标字段。

| 图表类型 | 必选配置 | 示例 |
| --- | --- | --- |
| 柱状图 | 维度、指标 | 按城市展示销售额 |
| 折线图 | 时间或有序维度、指标 | 按天展示订单量 |
| 饼图 | 维度、指标 | 按订单状态展示数量占比 |

例如查询已经返回：

```json
[
  { "status": "paid", "count": 120 },
  { "status": "pending", "count": 30 },
  { "status": "cancelled", "count": 10 }
]
```

选择维度 `status`、指标 `count`，即可画柱状图或饼图。此处 `count` 是查询已经计算的值，绘图时不应再按行数计数。

第一版支持单个维度字段和单个数值指标字段、悬停查看值、图例，以及当前结果内的配置保留。PNG 导出可作为随后的小迭代。多序列、按日期分桶、保存查询时携带图表配置，需要在基本工作流确认后再安排。

### 数据范围必须明确

AMDM 当前 Renderer 持有的是结果的一页；主进程保留同次执行的游标和磁盘分块缓存。分页不会重新运行脚本。依据：[结果状态](../src/renderer/src/lib/tabs.ts)、[分页实现](../src/main/mongo/shellResults.ts)、[架构约定](architecture.md)。

第一版采用当前页绘图，范围显示为「当前页 · N 条」。只有确认页面覆盖整个查询结果时，才显示「完整查询结果 · N 条」。不能仅因当前页是最后一页，就认为它包含完整结果；还需确认从结果起点开始且条数覆盖全部。

例如查询匹配 10 万条订单，但当前页只有 50 条：图表只代表这 50 条，饼图百分比的分母也是当前绘图数据。它不能标为所有订单的状态分布。第一页也不是随机抽样，不能称为代表性样本。

为了分析完整业务范围，初期推荐用户通过 MongoDB 聚合得到规模较小的统计结果，再绘图。聚合结果仍然可能有多页，必须遵守相同范围规则。

如后续支持「读取完整查询结果绘图」，应作为显式操作：复用同次执行的游标/缓存，分批处理，提供进度和取消，并设定读取字节数、文档数、图形点数预算。达到预算时明确显示未完成状态，不把截断结果当成完整统计。完整查询结果仍受用户原查询的 `skip`、`limit` 约束。

### 必须明确的数据语义

- 从原始 EJSON 值读取数字和日期，复用现有类型识别；不解析表格显示出来的字符串。嵌套字段先通过查询提取到顶层，数组先由查询展开。
- 缺失值与零不同。折线图中的缺失值保留缺口；不自动把缺失日期补成零。混合类型、无效数值应显示处理结果，不能静默转成零。
- 数值和时间横轴按其真实值排序。日期标签遵循应用时区；未来增加按天/月汇总时，分桶时区也必须明确。
- 重复维度值（含相同时间点）不能静默相加。第一版按行绘制；需要每个维度值对应一个指标值时由查询聚合。饼图遇到维度值重复时应提示先汇总指标，避免重复图例造成歧义。
- 饼图仅接受非负有限数值，且总和大于零。占比针对明确的绘图范围；不自动隐藏占比较小的维度值或改变分母。
- BSON Long、Decimal128 转换成绘图库数值可能损失精度；需保留原值用于提示，明确可绘制范围，不能让显示近似值变成统计计算来源。第一版不应宣称提供精确的本地财务聚合。

## 原始明细统计：后续能力

若用户输入的是订单明细，希望只选 `status` 就得到状态数量分布，则还需要「分组字段 + 统计方法」。例如按状态计数、按城市求金额之和、按天汇总订单数。

本地汇总只对选定的数据范围有效。对大量文档做完整统计，优先让 MongoDB 执行 `$match`、`$group`、`$sort` 等聚合，再返回图表需要的少量点。Atlas Charts 的官方执行机制也采用数据库端聚合，但 AMDM 的具体实现应遵循自己的 Shell 契约。[官方依据](https://www.mongodb.com/docs/charts/aggregation-pipeline-generation/)

如果增加可视化统计配置，建议生成可查看、可编辑的聚合查询，由用户明确执行。仅对已知的结构化数据源生成管道，不解析或自动重写任意 Shell 脚本；脚本可能包含变量、多次查询或写操作。也不能为了切换图表而重新执行脚本。

## AMDM 实现落点

1. `ResultPanel.tsx` 增加 Chart 视图入口；`ResultTab` 保存图表类型和字段映射，切换视图时保留，关闭结果时释放。
2. 复用 `resultFields.ts` 的字段发现及缓存机制、`ejson.ts` 的类型识别和现有时区上下文。现有字段发现主要面向顶层键；支持嵌套标量路径时只补充图表所需部分。
3. 将字段取值、数值转换、排序和校验写成独立纯逻辑。当前页绘图直接使用现有结果，不需要新增查询 IPC。
4. 绘图库候选为 Apache ECharts：官方 `dataset` 支持 bar、line、pie，并支持字段映射；可按需引入模块。采用懒加载，进入图表时再加载；其真实包体和交互性能需在实现时测量。[Dataset](https://echarts.apache.org/handbook/en/concepts/dataset/)、[按需引入](https://echarts.apache.org/handbook/en/basics/import/)
5. 完整结果读取是后续跨进程能力，需要额外设计取消、缓存所有权和预算；不能直接将所有文档送入 Renderer。若支持 Web 版，也需同步遵守已有 Web API 与结果所有权契约。

实现时验证范围应包括字段类型转换、缺失值、维度值重复、范围标识和结果配置生命周期；复杂数据量下再用当前 Electron Renderer 验证交互与内存。当前验证结果见上方「当前实现」；未运行完整回归或性能基准。

## 下一步需要确认的产品选择

最关键的是目标用户是否愿意先写聚合查询：

- 愿意：优先实现「已有查询结果 + 字段映射 + 三种图形」，可以较快验证价值。
- 希望完全通过选字段完成统计：需要把「分组 + 计数/求和 + 日期分桶 + 数据范围」一起纳入需求，工作量与语义复杂度明显更高。

建议先用三个真实任务验证候选方案：订单状态占比、每日订单趋势、各城市销售额。分别确认用户当前拿到的是明细还是汇总结果，以及他们需要当前页观察还是完整范围统计。
