# 查询运行时性能对比报告

> 历史基准记录：当前版本已统一使用 Mongosh，本文中的 AMDM driver 选择入口和产品建议不再适用。以下测量保留用于性能对比。

测试日期：2026-09-11  
代码基线：`51d2283`  
结论：Mongosh 在小结果查询中有约 4–5 ms 的固定额外开销，在大结果查询中差距很小；大量 `print` 调用的运行时开销明显高于 AMDM driver。对普通远程数据库查询，网络和服务端耗时通常会稀释这部分差异。

## 测试环境

- MacBook Pro，Apple M1 Pro（8 核），32 GB 内存
- macOS 26.5.1
- Node.js 24.11.1，pnpm 10.33.2
- MongoDB 8.2.6，单节点内存副本集
- 两个运行时复用同一个 `MongoClient`、数据库和测试数据

## 测试方法

先分别预热两个运行时，再交替执行相同查询，避免固定执行顺序偏向某一方。测试覆盖从数据库操作到 AMDM `ShellResult` 的完整主进程路径，包括运行时求值、结果适配和 EJSON 序列化，不包括 Renderer 绘制。

每组独立执行两轮，表格展示两轮的 P50 区间：

| 场景 | 每轮次数 | AMDM driver P50 | Mongosh P50 | 观察 |
| --- | ---: | ---: | ---: | --- |
| `findOne` 返回一个普通文档 | 40 | 0.86–0.93 ms | 4.30–4.69 ms | Mongosh 多约 3.4–3.8 ms |
| 查询并返回 50 个普通文档 | 30 | 1.24–1.52 ms | 5.57–6.59 ms | Mongosh 多约 4.3–5.1 ms |
| 查询并返回 50 个 128 KiB 嵌套文档 | 10 | 30.03–32.22 ms | 33.43–33.88 ms | 差距约 1.2–3.9 ms |
| 输出 1,000 行 Console 文本 | 20 | 0.81–0.83 ms | 20.62–30.25 ms | Mongosh 的纯运行时开销明显更高 |

## 冷启动和内存

已有打包应用测试显示：

- Mongosh 运行时首次准备约 113.8 ms；使用 V8 编译缓存后的下一次启动约 66.9 ms；同一进程内再次准备约 0.2 ms。
- 预加载 Mongosh 后，主进程 RSS 从 225,408 KiB 增至 270,832 KiB，增加约 44 MiB。
- Mongosh 采用按需加载，因此未选择它的用户不会承担这部分运行时加载成本。

当前没有同一打包进程下 AMDM driver 的独立 RSS 增量数据，内存部分不能作为严格的双向 A/B 结论。

## 结论

- 普通查询：Mongosh 的固定开销可测量，但绝对值约为数毫秒，不属于明显影响交互的差距。
- 大结果查询：数据库读取和序列化成为主要成本，两个运行时接近。
- Console 密集脚本：AMDM driver 明显更快，Mongosh 更完整的 Shell 求值和输出路径带来较高开销。
- 首次使用和内存：Mongosh 比 AMDM driver 更重；按需加载和编译缓存已经避免影响未使用 Mongosh 的启动路径。
- 产品选择：Mongosh 适合作为兼容性优先的默认运行时；对极低延迟或 Console 密集场景，可在设置中选择 AMDM driver。

## 限制

- 数据库运行在本机，网络延迟接近零，因此小查询的倍数差异会被放大；远程数据库更应关注绝对毫秒差。
- 每组样本量较小，结果用于判断产品级差异，不代表跨设备的通用基准。
- 测试未包含 Renderer 的 DOM 更新、表格绘制和虚拟滚动耗时。
- 两个运行时的功能集合不同，性能数字不能代替兼容性验证。
